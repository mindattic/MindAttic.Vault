## Context

Every MindAttic app with a settings/options screen builds its own (IdiotProof, Tutor, ThinkTank, Prose, Orchestrator, JobHunt, MediaButler, Browser, TaxRateCollector, ...), and each stores keys its own way. LLM keys get re-entered per app. A new user can't get going without hand-configuring every app.

RFC 0002 (M.VALT-T26, now wont-do) tried to fix this with a split **Vault.Web + Vault.Desktop** pair. Rejected: a web-hosted settings editor is a standing attack surface for credential-adjacent data, and running a web app locally just to edit settings is pointless.

Outcome wanted:
- **One native WPF app, `MindAttic.Vault.Desktop`**, never network-exposed, is the only place any app's settings or secrets are edited.
- **Profiles**: `Desktop` (local AppData) and `Azure` (Key Vault + App Configuration), with more to come. Same tabs and fields in every Profile; only the backend changes. On the Azure Profile, Load pulls the live values into the fields and Save writes them back, so you never use the Azure portal.
- **LLM keys shared across every app** through Vault, with **several keys per provider** you can switch between when one stops working.
- **Remembers its last state** (Profile, tab, selected keys, window).
- **First run works out of the box**: every non-secret setting has a shipped default, so a new user only brings their own keys (BYOK).
- Every app's own settings screen goes away; its cog opens Vault.Desktop at its tab.

## Decisions (from the user, 2026-10-31)

- LLM keys: **one shared, named list of keys per provider for the whole workspace** (e.g. `ClaudeApiKeys["key1"]`, `ClaudeApiKeys["2026-10-31 IdiotProof"]`). **An app overrides by picking which named key(s) from that list it uses** — never by holding its own copy of a key.
- **Everything is Name/Value**: every setting and every key has one readable full name that is the same in the UI, the local files, App Configuration and the deployed app's `IConfiguration`.
- A key that fails (401/403/quota): **apps fail over to the next key automatically, and the bad key is flagged** in Vault.Desktop.
- First-run defaults live **in each app's own settings class** (property initializers); Vault writes them to disk on first run.
- App tabs are **generated from each app's settings manifest** (no app UI code inside Vault.Desktop).
- Local keys **stay plain text** in `providers.json` (no DPAPI); protection is the user's Windows profile folder permissions.
- Delivery: **everything at once** — Desktop and Azure Profiles, key pools, first-run, every app migrated. Work is still ordered by dependency (phases below); nothing ships half-done.

## Design

### 0. What counts as a setting (scope line)

Vault.Desktop owns **every app-level and machine-level setting and every key** — anything one person configures once for an install or a deployment. It does **not** own data that belongs to the app's own users or content, because a single-person desktop tool can't sensibly edit another user's data:
- IdiotProof per-user `SettingsKv` / `UserPreferences` (each trader's own limits) — stays in IdiotProof's UI; IdiotProof's app-level settings move.
- Prose per-universe `Setting` rows — stays in Prose; Prose's app-level settings move.
- MindAttic.Ideas site and widget-instance settings (CMS content) — stays in Ideas; its app-level settings move.
- JobHunt (single-row SQLite `AppSettings`) and Orchestrator (`JsonStore` in its db) are single-machine: their settings **move entirely** to Vault (`JsonSettingsStore`), with a one-time import from the database on first run.

Each migrated app keeps a settings screen only for user/content data; the cog for app-level settings opens Vault.Desktop.

```
MindAttic.Vault (core NuGet, no Azure SDK, no UI)          used by every app
  ISettingsStore<T>, JsonSettingsStore<T> (Desktop backend)
  settings manifest: [Setting]/[SettingsApp] attributes -> settings.manifest.json
  LoadOrSeed (first-run defaults), key pools + key health + KeySelector (failover)
  ConfigurationCredentialStore learns named key lists + app assignments (Azure read path)

MindAttic.Components.Wpf (NuGet)                            shared UI
  + MaSecretBox, + AsyncRelayCommand, + MaCheck style (M.COMP-T121)

MindAttic.Vault.Desktop (WPF exe, in the Vault repo, not packaged)   the only editor
  Profiles: DesktopProfile, AzureProfile (Azure SDKs live only here)
  tab per app, generated from that app's manifest
  Keys tab: shared provider pools, health, per-app overrides
  Get Started checklist (BYOK), remembered state, audit log
```

### 1. One settings contract in Vault core

- Extract `ISettingsStore<T>` (`Exists`, `Load`, `LoadAsync`, `Save`, `SaveAsync`, `Update`, plus `LoadOrSeed`) from `JsonSettingsStore<T>`. `JsonSettingsStore<T>` implements it unchanged. `AddVaultAppSettings<T>` registers the interface.
- **`LoadOrSeed()`**: if the file doesn't exist, save `new T()` (the app's property-initializer defaults) atomically and return it. This is MediaButler's `SettingsService.Load()` pattern moved into Vault so every app gets it. Existing files are never overwritten.
- No secret ever lives in a settings class. Secrets stay in credential stores (that's already how Vault is built; now it's a rule with a test).

### 2. Settings manifest — tabs are generated, not hand-built per app

Instead of each app shipping its own settings screen (Razor or WPF) for Vault.Desktop to host, each app **describes** its settings and Vault.Desktop **renders** them. Reasons: the user said every field is fixed per app; no app UI code ever runs inside the secrets app; no BlazorWebView (no browser engine in the secrets app); Desktop never has to be rebuilt when an app adds a setting; works the same for WPF, Blazor and console apps.

- Attributes in Vault core: `[SettingsApp(Id, DisplayName, Icon)]` on the settings class; `[Setting(Label, Group, Help, Order)]` on properties; optional `[Range]`, `[Choices]`, `[PathPicker(File|Folder)]`, `[Url]`, `[Multiline]`. Field kind is inferred from the property type (string, bool, int/decimal, enum, string list, path, url, TimeSpan).
- `[UsesCredential(ProviderId, Required, Purpose)]` on the settings class declares which key pools the app needs (e.g. `claude`, `openai`, `alpaca`). This drives the Get Started checklist and the app tab's "Keys used" section. No key value ever appears in the manifest.
- On every startup, `AddVaultAppSettings<T>` (or `LoadOrSeed`) writes `settings.manifest.json` next to `settings.json` in the app's bucket: schema version, app id, fields, defaults, credentials used. Atomic write; only rewritten when content changes.
- Vault.Desktop discovers apps by scanning `%APPDATA%\MindAttic\*\settings.manifest.json` and keeps the tab list in sync with `CollectionSync.SyncBy` (Orchestrator's `MainViewModel.Tabs.cs` pattern).
- An app that hasn't run yet has no manifest. Each app's install/`run.ps1` runs it once with `--write-settings-manifest` (seed + manifest, then exit) so a fresh ecosystem install shows every app immediately.
- Extending: a new field kind = one `IFieldEditor` (a DataTemplate + a value converter) registered in Desktop. Nothing else changes.

### 3. Names, and LLM keys shared across all apps (named keys, selection, health, failover)

**Naming (Name/Value everywhere).** Every value has one canonical name in `IConfiguration` path form, `Section:Name`:
- App settings: `{AppId}:{Property}` — e.g. `IdiotProof:MaxLossPerTrade = 50`. The local `settings.json` keeps today's JSON shape, whose paths are exactly these names, so existing files and code don't change.
- Keys: `Llm:{provider}:ApiKeys:{keyName} = <secret>` — the user's `ClaudeApiKeys["2026-10-31 IdiotProof"]` is `Llm:claude:ApiKeys:2026-10-31 IdiotProof`. Key names are free text you choose (trimmed, unique per provider, no `:`), shown everywhere; they are the key's identity.
- Which keys an app uses: `{AppId}:Keys:{provider} = ["2026-10-31 IdiotProof", "key1"]` — a **non-secret ordered list of key names**; the first is the app's **active key**, the rest are its fallbacks. Missing = use the shared list in its default order.
- Desktop shows every field's full name (copyable) next to its label, so any value can be found by name in files, App Configuration or logs.

**Named key lists.**
- The existing `LlmCredentialStore` bucket becomes the workspace-wide named list per provider. `CredentialPoolEntry`'s `Label` becomes the required, unique **Name** (old unlabeled entries are named `key1`, `key2`... on first load), plus an optional `Disabled` flag. `providers.json` stays back-compatible: single-key and today's `apiKeys:[{key,label}]` files both load.
- Order of the shared list = default failover order. Rename keeps the key's health and every app's selection pointing at it (Desktop rewrites the references in one atomic operation and audits it).
- **Keys are managed only on the Keys tab; apps are assigned keys on their own tab.** Each app tab has a "Keys" section with one row per provider the app uses (`[UsesCredential]`): an **Active key** picker (`MaPicker` listing the provider's key names, each with its status light) and an optional ordered **Fallback keys** list. Choosing `2026-10-31 IdiotProof` stores only names: `IdiotProof:Keys:claude = ["2026-10-31 IdiotProof", ...fallbacks]` (first = active). "Use shared default" clears the assignment. Deleting a key that an app still has assigned is blocked with "assigned to IdiotProof, Tutor" until you reassign. No secret is ever copied per app (replaces the old `AppScopedCredentialStore` override idea).
- Resolution in apps: `KeySelector` reads the app's selected names (or the shared order), then the values from the shared list.

**Provider catalog (one list for everyone).** Vault core gets a static `ProviderCatalog`: id, display name, category (LLM, broker, media, TTS, other), key-page URL, aliases. Canonical LLM ids from the inventory: `claude` (alias `anthropic`), `openai`, `gemini` (alias `google`), `deepseek`, `kimi`, `mistral`, `grok` (alias `xai`), `groq`, `perplexity`, `cohere`, `openrouter`, `ollama`; non-LLM: `alpaca` (broker), `elevenlabs` (TTS), `jellyfin` (media). Aliases resolve on read, so `anthropic` and `claude` keys merge into one list. The Keys tab groups by category, so non-LLM keys (Alpaca, ElevenLabs, Jellyfin) get the same named-list treatment. Legion's provider list is reconciled to this catalog.

**Migrating today's per-app key copies.** Automata, MediaButler, Tutor, IdiotProof, JobHunt and TaxRateCollector wrap the keyring in `AppScopedCredentialStore` today. On first run of the new Vault, each app-scoped key is moved into the shared list (named `{app} (imported)`, deduplicated if the value already exists under another name) and set as that app's active key. Behavior is unchanged and no copies remain. Same for keys in `.key` override files, env vars the apps read today (`JF_API_KEY`, `ELEVENLABS_API_KEY`) and `legion.json`: the import is offered on the Get Started screen, never silent.

**Key health is observed state, kept separately**: `%LOCALAPPDATA%\MindAttic\Vault\key-health.json` keyed by `{provider, keyName}` (never the key or a hash of it): last success, last failure, failure kind, cool-down-until. Written atomically (LAW-6), shared by every app on the machine, so a key one app finds broken is skipped by all.
- **`KeySelector`** (new, core): `ExecuteAsync(providerId, appId, Func<string key, Task<T>> call)` tries the app's active key, then its fallbacks in order (or the shared order when the app has no assignment), skipping disabled and cooling-down ones. It classifies the result: auth failures (401/403) mark the key failed (needs you), quota/429 sets a cool-down (honors Retry-After), network errors don't blame the key. On success it records health and returns. When every key fails it throws one `AllKeysFailedException` listing providers and failure kinds, never keys. Apps call LLMs through this instead of `GetKey()`.
- Desktop's **Keys** tab: one section per provider listing its named keys in default order (drag to reorder) — name, masked value (`MaSecretBox`), status light (healthy / cooling down / failed / disabled / never used), last used, "used by" apps, Test (one cheap authenticated call through the same classifier), add / rename / disable / remove.

### 4. Profiles

- `IProfile { Id, DisplayName, bool IsReady, ISettingsBackend For(AppManifest), IRotatingKeyStore Keys(appId) }`. Registered in Desktop; the profile picker binds to the list. A future platform is one new class.
- **Desktop Profile**: `JsonSettingsStore<T>` (untyped JSON variant driven by the manifest, since Desktop doesn't reference app assemblies) and the file credential stores.
- **Azure Profile**: one environment = (app → Key Vault + App Configuration store) mappings, picked once per app through the resource picker and remembered.
  - Sign-in: `InteractiveBrowserCredential` with a persisted, OS-encrypted MSAL token cache (`TokenCachePersistenceOptions`), so you sign in once. Your own identity; no secrets stored by Desktop for Azure access.
  - Picker: `Azure.ResourceManager` lists subscriptions → resource groups → Key Vaults / App Configuration stores.
  - **Names live in App Configuration, secret values live in Key Vault.** Every name from section 3 is an App Configuration key with exactly that name (App Configuration allows spaces, so `Llm:claude:ApiKeys:2026-10-31 IdiotProof` is stored as-is). Plain settings hold their value; key entries hold a **Key Vault reference** to the secret. ETag optimistic concurrency on every write.
  - Key Vault secret names only allow letters, digits and dashes, so each secret gets a generated name (`llm-claude-<slug>-<6-char id>`) and carries the readable key name in a `name` tag. You never see or type it; App Configuration's reference maps the readable name to it. One naming function, contract-tested. Save writes a new secret version; rename only changes the App Configuration key and the tag.
  - Deployed apps stay read-only (LAW-4) and read everything by name through `IConfiguration` using the App Configuration provider with Key Vault reference resolution, wired by the **host** (LAW-5: the core package still has no Azure SDK). `ConfigurationCredentialStore` gains named-key-list reading (`Llm:{provider}:ApiKeys:*`) and app selections (`{AppId}:Keys:{provider}`), so selection and failover behave the same in Azure as locally.
  - Missing RBAC role (Key Vault Secrets Officer / App Configuration Data Owner) gets a plain explanation of which role is needed on which resource, not a stack trace.
  - After Save, Desktop says when the app will see it (App Configuration refresh vs restart).
- Load / edit / Save is identical in every Profile. Dirty tracking per field; Save writes only changed fields; Revert reloads.

### 5. Remembers its state

`VaultDesktopState` (non-secret) via `JsonSettingsStore<VaultDesktopState>` in the `Vault.Desktop` bucket: last Profile, last tab, window bounds (clamped to a monitor that still exists), theme, collapsed groups, Azure environment mappings. Saved debounced on change and on exit. Corrupt/missing file → defaults (that's `JsonSettingsStore`'s existing behavior).

### 6. First run / BYOK

- Every app seeds its own defaults (`LoadOrSeed`) and writes its manifest, so nothing is blank except keys.
- Desktop opens on **Get Started** when any required credential (`[UsesCredential(Required=true)]`) has no key: one row per provider ("Claude — needed by Tutor, Prose, IdiotProof"), a key field, a link to that provider's key page, and Test. Done when every required provider has a working key; it then never shows again unless a required key goes missing.

### 7. Opening from an app

- Re-file the open-my-settings helper (M.COMP-T153's code was reverted in Components `a9391c4`): `VaultSettings.Open(appId)` launches or activates Vault.Desktop at that app's tab.
- Single instance: copy Orchestrator's `SingleInstance.cs` (named mutex + show event + `PipeOptions.CurrentUserOnly` pipe). Desktop accepts exactly one argument shape, `--app <id>`, length-capped, validated against discovered manifests; anything else is ignored and logged.
- Each app deletes its own settings screen/route/window and points its cog at the helper.

- Desktop uses `Microsoft.Extensions.DependencyInjection` (no Generic Host). Existing WPF apps hand-compose, but Vault already exposes `IServiceCollection` extensions and DI makes every ViewModel testable with fakes.
- MVVM on `MindAttic.Components.Wpf.Mvvm` (`ObservableObject`, `RelayCommand`, new `AsyncRelayCommand`). Views are DataTemplates keyed by ViewModel type in `App.xaml`.
- Startup copies the house pattern: `MaToolTips.KeepOpen()`, three unhandled-exception hooks, Serilog → MindAttic.Log (`TicketsLog.cs` shape), `MaTheme`, `MaWindow.SetThemedTitleBar`.

## Security

Threat model: local malware/other users on the machine, accidental leaks (logs, screenshots, clipboard history, crash dumps, git), a compromised app on the ecosystem, Azure credential misuse.

1. **No network listener, ever.** No Kestrel, no WebView, no HTTP server. Only outbound HTTPS to Azure and to LLM providers for Test. Pipe is `CurrentUserOnly` and accepts only `--app <known id>`.
2. **Secrets are write-mostly in the UI.** New `MaSecretBox` (Components): masked by default; Reveal needs a click and hides again after 30 s or when focus/window changes; the automation/accessibility name never contains the value; Copy puts the value on the clipboard excluded from clipboard history/cloud sync and clears it after 30 s. Values are held only in the edit buffer, never in a bindable string property that logging or diagnostics could read.
3. **Never logged.** A Serilog destructuring/enricher policy redacts anything typed as a secret; audit and diagnostic messages carry field names and key `Id`s, never values or hashes. Canary-secret tests enforce it (Testing #6).
4. **Audit.** Every Save appends one entry: time, Windows user (and Azure UPN on Azure), Profile, app, fields changed (secrets as "changed", no value). Append-only SQLite at `VaultPaths` local `Vault\audit.db` with insert-only triggers (the Tickets DB technique). Audit write failures are logged, not thrown (IdiotProof `AuditLogRepository` convention). Azure writes also land in Azure's own Key Vault/App Configuration logs.
5. **Local keys at rest: plain text, by decision.** `providers.json` stays readable JSON under `%APPDATA%\MindAttic\`. Desktop checks at startup that the Vault folders aren't readable by other users or Everyone (a too-open ACL shows a warning with a one-click fix), and keys are never written anywhere else locally (no state file, temp file, log or crash dump).
6. **Least privilege on Azure.** Your own identity, interactive sign-in, OS-encrypted token cache; the exact RBAC roles are documented; production apps keep managed-identity read-only access (LAW-4).
7. **Concurrency and integrity.** Atomic writes (LAW-6); file watcher warns when another process changed a file you're editing; ETags on App Configuration; Azure Save shows a confirm listing changed field names (never values).
8. **Input handling.** Values are validated by kind (Range, Url, Path) before Save; path pickers don't follow into other users' profiles; manifests are parsed with size limits and unknown kinds render read-only rather than crash.
9. **Supply chain.** Exact package versions: `Azure.Identity 1.21.0` (match the workspace), `Azure.Security.KeyVault.Secrets 4.11.1` (match MindAttic.Ideas), current stable `Azure.Data.AppConfiguration`, `Azure.ResourceManager`, `.KeyVault`, `.AppConfiguration` pinned exactly. Only Vault.Desktop references them.
10. **Crash safety.** Unhandled-exception handlers log type/message/stack only; no ViewModel dumps.
